# Agent Note: 模型设置页可编辑第三方模型的思考强度档位

Status: implemented

[English](2026-08-13-web-third-party-reasoning-effort-editor.md) | 中文

## 问题

输入框的模型选择器提供推理等级面板，但手工声明的第三方模型永远拿不到它：决定面板内容的是 profile 里的 `reasoningEfforts` 声明（[按模型声明推理等级](../../implemented/feature/2026-08-08-pi-ai-per-model-reasoning-declarations.md)），而模型设置页——这类路由唯一的编辑面——刻意不提供任何推理控件，理由是推理是按模型的能力、没有提供方级的答案。于是只通过 Web 界面配置私有网关思考模型的用户只能手写 `settings.yaml`，从界面到选择器本就具备的能力之间没有任何可发现的路径。

该字段本就是一个「承载但不编辑」的槽位：`ModelDraft` 结构开放，行 patch 展开已存行再应用改动，采纳候选时已有行优先于重新发现的候选，因此手写的 `reasoningEfforts` 在编辑其他字段时能存活。缺的只是编辑器。

## 决策

每条 pi-ai 模型行的展开区（与容量同一个折叠区）新增一个**思考强度档位**文本字段。它把已存 `reasoningEfforts` 的键读成逗号分隔列表，并把输入写成规范的 `id → wire 拼写` 映射：每个输入的 id 只在属于 pi-ai 规范档位（`off`、`minimal`、`low`、`medium`、`high`、`xhigh`、`max`）时才被接受，`off` 映射为 `null`（支持、不发送任何东西），其余映射为自身。未知档位会被拒绝且不丢弃已输入文本，并点名违规档位。当输入的档位集合与已存键一致时，保留已存的 wire 拼写——把声明里 `max` 改名为 `ultra` 的网关，在只重排或复述档位时能保留该拼写。

档位词汇从 `llm-pi-ai` 的 `THINKING_LEVELS` 镜像而来，因为源码平面分割禁止 client 包导入适配器；两者若漂移，会在保存时于适配器自己的 schema 处响亮失败，而不是悄悄收窄可选项。

保存后的声明原样走既有链路：`catalog.ts` 以 `reasoning: true` 与拼写映射物化模型，`reasoningInfo` 报告档位，选择器的推理等级面板恰好提供这些档位。选择器与持久化 seam 均无需改动。

输入框的模型座位新增了第二个触发器，让档位不必埋在模型菜单里。当当前模型携带推理元数据时，模型触发器左侧会渲染一个独立的**思考强度按钮**，显示当前档位并直接打开档位面板；没有该元数据时按钮不渲染，因此不提供档位的模型不会出现一个无效控件。两个触发器共用菜单与选择提交，焦点会回到打开菜单的那一个。

## 结果

- 只通过 Web 界面就能端到端配置手工声明路由上的思考模型：在行里声明档位，再到输入框选择模型与等级。
- 档位集合即全部可选项，与声明语义一致：未输入的档位不会被提供，也没有「继承 catalog」的写法。想要 catalog 档位的用户需复述它们。
- `input`、`compat` 及其余 settings 文档字段仍不由表单编辑；只有 `reasoningEfforts` 加入了 `id`、`name` 与两个容量之列（[输入模态笔记](../../implemented/architecture/2026-08-12-pi-ai-route-default-input-modalities.md)）。
- DeepSeek 适配器家族不受影响：其行走独立的 `DeepSeekModelsEditor`，模型不携带 `reasoningEfforts`。

## 备选方案

- **规范档位的下拉框。** 无法作为单一控件使用，因为该字段表达的是一个*集合*——模型声明它接受哪些档位，选择器把集合转成逐项选择。
- **存下任意输入文本。** 适配器的 schema 会在保存时拒绝未知键，于是拒绝会点名写入而非字段。行内校验在用户仍看着字段时点名违规档位。
- **逐档位编辑 wire 拼写。** 适配器刻意把协议拼写保持私有；规范 id 表面正是声明本身采用的面向运维的形态。
